1. COMPLETE SEARCH FLOW  (what actually happens on one query)
================================================================================

Example query: "payment terms"

--------------------------------------------------------------------------------
STEP 1 — USER TYPES IN THE SEARCH BAR
--------------------------------------------------------------------------------
File:      frontend/components/layout/SearchBar.tsx  (1027 lines)
Function:  handleChange -> setTimeout(fetchResults, RESULTS_DEBOUNCE_MS)
Does:      Waits 280 ms after typing stops. Only fires if the query is at least
           2 characters. Separately schedules the AI answer call at 1200 ms
           (or immediately if the query looks like a question).
Receives:  The raw text the user typed.
Returns:   Nothing — it triggers the API call.
Note:      The fast search request has NO AbortController (only the AI request
           does), so stale responses are discarded by comparing the query string.

--------------------------------------------------------------------------------
STEP 2 — FRONTEND API CALL
--------------------------------------------------------------------------------
File:      frontend/lib/api.ts
Function:  searchApi.searchFast(query)
Does:      POSTs to {API_URL}/api/search/results using an axios client that
           attaches "Authorization: Bearer <token from cookie>".
Receives:  query string
Returns:   Promise<SearchResponse>
Note:      60-second timeout. Sends NO correlation ID and NO tenant header.

--------------------------------------------------------------------------------
STEP 3 — BACKEND ROUTE + AUTHENTICATION
--------------------------------------------------------------------------------
File:      backend/app/api/routes/search.py
Function:  fast_search(request, db, current_user)
Does:      Rejects an empty query with 400. Builds the context dict
           {"db": session, "user": User} via _context(). Gets the pipeline.
Receives:  SearchRequest body + the JWT
Returns:   SearchResponse

Auth happens in:
File:      backend/app/api/deps.py
Function:  get_current_user()
Does:      Reads the bearer token, checks a 90-second in-memory cache keyed by
           the RAW token string, and on a miss calls decode_token() and loads
           the User row from the database.
Receives:  Authorization header
Returns:   User object (or raises 401)

--------------------------------------------------------------------------------
STEP 4 — ORCHESTRATION
--------------------------------------------------------------------------------
File:      backend/app/search/pipeline_factory.py
Function:  get_search_pipeline()  (lru_cache, built once)
Does:      Wires the pipeline together: registers plugins, picks the default
           connector ("multi_database"), and injects four callables —
           analyze_query, filter_for_query, filter_for_display, generate_answer,
           plus get_cached_results.
Returns:   A SearchPipeline instance

File:      backend/global_search_core/pipeline.py
Function:  SearchPipeline.search_results(request, context)
Does:      The actual orchestration:
             analyze -> retrieve -> filter -> build response
Receives:  SearchRequest + context
Returns:   SearchResponse

--------------------------------------------------------------------------------
STEP 5 — QUERY UNDERSTANDING  (no LLM here)
--------------------------------------------------------------------------------
File:      backend/app/search/query_intel.py
Function:  analyze_query(query, default_top_k=8)
Does:      Pure rules, no network call. Detects:
             - is this a question?          is_question()
             - which content types?         detect_content_types() via the
                                            DOMAIN_SIGNALS keyword map
             - status hints                 detect_status_hints()
             - the BM25 search text         extract_search_terms()
             - a dynamic top_k              8 normally, 10 for questions,
                                            15 for workforce, 50 for filter
                                            queries like "0% progress"
Receives:  the query string
Returns:   QueryAnalysis(original, is_question, search_text, content_types,
                         status_hints, top_k)

Also:
File:      backend/app/search/query_planner.py
Function:  plan_query(query, analysis, filter_type, top_k)
Does:      Picks a retrieval MODE: SEMANTIC / FILTER / LIST_ALL / WORKFORCE.
           Exhaustive modes bypass top-K truncation (cap 100).
Returns:   QueryPlan

--------------------------------------------------------------------------------
STEP 6 — SOURCE SELECTION
--------------------------------------------------------------------------------
File:      backend/app/core/data_sources.py
Function:  select_sources_for_analysis(analysis, source_ids)
Does:      Maps content_types to source ids using hardcoded rules, e.g.
             content_types == ["team"]        -> buildtrack only
             all types are Space event types  -> space only
             BMS keywords                     -> space-bms only
           If nothing matches, it FALLS BACK TO ALL ENABLED SOURCES.
Receives:  QueryAnalysis
Returns:   list[DataSource]
Note:      "payment terms" matches nothing, so it fans out to all 17 enabled
           Space databases.

--------------------------------------------------------------------------------
STEP 7 — FAN-OUT ACROSS SOURCES
--------------------------------------------------------------------------------
File:      backend/app/connectors/multi_database.py
Class:     MultiDatabaseConnector
Function:  retrieve(context, query, filter_type, top_k, analysis)
Does:      1. Checks the shared result cache (key = md5 of
              query|filter|top_k|analysis_suffix|"multi:<source ids>", TTL 120s).
              *** This key contains NO user identity. ***
           2. Submits one job per source to ThreadPoolExecutor(max_workers=4)
              and collects with as_completed().
           3. Each source is wrapped in try/except, so a failing source returns
              an empty list and only logs a warning. There is NO per-source
              timeout.
Receives:  context, query, analysis
Returns:   list[SearchHit]  (SearchHit is just dict[str, Any])

--------------------------------------------------------------------------------
STEP 8 — PER-SOURCE RETRIEVAL
--------------------------------------------------------------------------------
File:      backend/app/connectors/buildtrack.py
Class:     BuildTrackConnector
Function:  retrieve(...)
Does:      Branches by source type:

   (a) Space databases  -> app/search/space_hybrid.py retrieve_space_hybrid()
         - routing/source_router.py route_query() scores keywords: DB / TOOL / BOTH
         - if the query looks structured, runs the SQL agent:
             app/sql_agent/pipeline.py  run_schema_sql_retrieval()
             app/sql_agent/generator.py generate_select_sql()  <-- LLM CHAT CALL
             app/sql_agent/validator.py validate_select_sql()  (regex read-only
                                        guard, table allowlist, forced TOP N)
             app/sql_agent/executor.py  execute_readonly_sql() (15s timeout, 50 rows)
         - may also hit the Azure index with security_filter=None

   (b) SQL-only sources -> app/search/sql_source_search.py sql_search_documents()
         Reads a pre-flattened "search_documents" table. Scores by token
         overlap: score = hits + title_hits * 1.5

   (c) Azure-indexed sources -> app/search/retrieval.py hybrid_search()

Returns:   list of hit dicts, each tagged by _tag_hits_with_source() with
           metadata.database_id / database_label and id prefixed "{source_id}::"

--------------------------------------------------------------------------------
STEP 9 — AZURE AI SEARCH HYBRID RETRIEVAL
--------------------------------------------------------------------------------
File:      backend/app/search/retrieval.py
Function:  hybrid_search(query, filter_type, top_k, analysis, search_index,
                         security_filter)
Does:      - Builds an OData filter from filter_type (content_type eq 'x') and
             merges in security_filter if one was passed.
           - Decides whether to embed the query:
                _should_embed = analysis.is_question or len(query.split()) >= 5
             If yes, fires embed_text() in the background so it overlaps the
             BM25 round trip.
           - Fast path: BM25 only (8s cap).
             Deep path: semantic + keyword in parallel (10s cap each).
           - Attaches a VectorizedQuery when a vector arrived in time.
           - Merges the sub-searches with _merge_results() (dedupe on id).
Receives:  query + QueryAnalysis + index name + optional OData security filter
Returns:   list of hit dicts with score = @search.score

Supporting:
  app/search/embeddings.py  embed_text()   text-embedding-3-small, 1536 dims
  app/search/indexer.py     get_search_client()  AzureKeyCredential
  app/search/blob_retrieval.py  search_blob_content()  document chunk / RAG index

--------------------------------------------------------------------------------
STEP 10 — RESULT PROCESSING / ENRICHMENT
--------------------------------------------------------------------------------
File:      backend/app/search/document_enrich.py
Function:  enrich_document_results(db, hits)
Does:      Patches stale index rows with live SQL values (title, file type,
           uploader) and rewrites id/url.

File:      backend/app/search/hydrate.py
Function:  enrich_hits_from_sql(hits, context, user)
Does:      Re-reads authoritative rows from SQL ("DB is source of truth").
           Calls _authorize_row() — but note it NEVER DROPS a hit that fails
           the check; it only skips merging the SQL fields.

File:      backend/app/search/cross_db_links.py
Function:  attach_related_hits(hits, query, max_related)
Does:      Adds related records from other databases (see section 2).

--------------------------------------------------------------------------------
STEP 11 — RANKING
--------------------------------------------------------------------------------
File:      backend/app/search/query_intel.py
Function:  rerank_score(item, analysis)
Does:      final_score = azure_base_score + sum(boosts). The boosts are the
           POC's real "search intelligence":
             content_type matches the detected type      +12  (miss: -10)
             workforce query and the hit is a team row   +20  (others: -25)
             project qualifier match >= 0.6              +10  (>=0.3: +3)
             status hint found in the text               +5   (in metadata: +6)
             exact upload-date match                     +30
             document-content query + document hit       +28
             blob RAG chunk answering a question         +20
             drawing-content query + drawing hit         +40
             token overlap with the question             up to +4
Returns:   a float

Applied in retrieval.py: items are re-scored, sorted desc, then sliced to
effective_top.

File:      backend/app/connectors/multi_database.py
Function:  _merge_by_score(hit_lists)
Does:      Merges every source's list, sorts by score descending.

File:      backend/app/search/result_filter.py
Function:  filter_results_for_query(query, results, analysis)
Does:      Applies a relevance threshold: min_score = max(8.0, top_score * 0.55)
           (0.72 for "which drawing" style queries), plus type/role filters
           driven by the query text.
Returns:   the trimmed list

--------------------------------------------------------------------------------
STEP 12 — RESPONSE
--------------------------------------------------------------------------------
File:      backend/global_search_core/pipeline.py
Function:  SearchPipeline._to_items() and _sources_from_hits()
Does:      Converts hit dicts to SearchResultItem and lists which sources
           answered. total_results = len(filtered).
Returns:   SearchResponse

--------------------------------------------------------------------------------
STEP 13 — RENDER AND NAVIGATE
--------------------------------------------------------------------------------
File:      frontend/components/layout/SearchBar.tsx
Function:  handleResultClick(result)
Does:      router.push(result.url) — the URL comes FROM THE BACKEND.
           Files go through frontend/lib/fileAccess.ts instead.

--------------------------------------------------------------------------------
PARALLEL TRACK — AI ANSWER (separate request)
--------------------------------------------------------------------------------
POST /api/search/answer -> SearchPipeline.search_with_answer()
  -> app/search/answer.py generate_answer(query, results, analysis)
     gpt-4o-mini, temperature 0.1, JSON response format, 280–700 max_tokens.
     Many deterministic paths run FIRST (manager lookup, handover workflow,
     extractive document answers) and skip the LLM entirely.
     Falls back to _fallback_answer() if Azure OpenAI is not configured.
  IMPORTANT: generate_answer runs on the RAW hits, before filter_for_display().

2. WHAT ACTUALLY MAKES THIS A "GLOBAL SEARCH"
================================================================================

These eight capabilities are the product. Everything else is scaffolding.

(1) SEARCHING MULTIPLE DATABASES
    backend/app/core/data_sources.py
      - DataSource dataclass (id, label, database_url, search_index, enabled,
        retrieval_mode)
      - list_configured_sources() builds 19 sources: buildtrack, assets, and 17
        Space databases
      - _engine_for() / session_for() cache one SQLAlchemy engine per source
    backend/app/core/space_databases.py
      - _KNOWN tuple hardcodes all 17 Space DB names and schema names
      - resolve_space_database_url() derives sibling URLs by SWAPPING THE
        DATABASE NAME inside a base connection string
    backend/app/connectors/multi_database.py
      - MultiDatabaseConnector.retrieve() fans out with
        ThreadPoolExecutor(max_workers=4) + as_completed()

(2) SEARCHING DIFFERENT KINDS OF DATA SOURCES
    backend/app/connectors/buildtrack.py  BuildTrackConnector.retrieve()
      Three retrieval styles behind one interface:
        Azure AI Search index   -> app/search/retrieval.py hybrid_search()
        Space schema + SQL      -> app/search/space_hybrid.py retrieve_space_hybrid()
        Plain SQL table         -> app/search/sql_source_search.py
      Document chunks           -> app/search/blob_retrieval.py

(3) DECIDING WHICH SOURCE TO SEARCH
    backend/app/core/data_sources.py  select_sources_for_analysis()
      content_type -> source_id rules; fallback is "search everything"
    backend/app/routing/source_router.py  route_query()
      Keyword scoring that picks DB vs TOOL vs BOTH. Despite the comments this
      is NOT semantic and uses no embeddings.
    backend/app/search/catalog/loader.py  sources_for_content_types()
      YAML-driven entity -> source mapping

(4) SEARCHING AZURE AI SEARCH
    backend/app/search/indexer.py
      ensure_index_exists()  — the index schema (see below)
      get_search_client() / get_index_client()
      index_documents()      — push upload, batches of 50, hash-gated embedding
    backend/app/search/retrieval.py  hybrid_search()  — BM25 + semantic + vector
    backend/app/search/blob_retrieval.py  search_blob_content()  — chunk index
    Indexes in use:
      buildtrack-index         entity rows from the primary DB
      buildtrack-assets-index  equipment / vendors / materials
      space-action-index       Space action.* tables
      space-schema-index       table and column DESCRIPTIONS (not row data)
      rag/blob index           document chunks — created in the Azure Portal,
                               NOT defined anywhere in this repo
    Index fields: id, title, content, content_type, url, metadata, search_text,
      search_text_hash, entity_id, entity_type, source_database, updated_at,
      project_id, organization_id, tenant_id, access_groups, location, status,
      progress_pct, record_status, content_vector (1536, HNSW), semantic config
      "default".

(5) COMBINING RESULTS
    backend/app/connectors/multi_database.py  _merge_by_score()
    backend/app/search/retrieval.py           _merge_results()
    backend/app/search/space_hybrid.py        _dedupe()
    backend/app/search/blob_retrieval.py      merge_sql_and_blob_hits()

(6) RANKING RESULTS
    backend/app/search/query_intel.py   rerank_score()      <- the real logic
    backend/app/search/result_filter.py filter_results_for_query()  (threshold)
    backend/app/search/query_planner.py plan_query()        (fetch sizes, modes)

(7) REMOVING DUPLICATES
    multi_database._merge_by_score():  first on id, then on
                                       "content_type|title.lower()|database_id"
    retrieval._merge_results():        on id only
    space_hybrid._dedupe():            "content_type|title|id"
    result_filter._dedupe_asset_results(): "content_type|title"
    Cross-source id collisions are prevented by prefixing "{source_id}::{id}"
    in buildtrack.py _tag_hits_with_source().

(8) LINKING RELATED RESULTS
    backend/app/search/cross_db_links.py  attach_related_hits()
      Roughly 16 hardcoded "hops" (_SPACE_PROJECT_HOPS). Given a hit that
      carries a ProjectId, it runs a separate query in each sibling database and
      joins the results in memory. There is no SQL join across databases.
      Examples of the links it assumes:
        any Space hit -> space-project.project.Project      via ProjectId
        any Space hit -> space-hse.Occupational_Review      via ProjectId
        any Space hit -> space-dms.Document                 via DimensionId
                                                            where DimensionType='PROJECT'
        any Space hit -> space-um.Users                     via User_Assignment.ProjectId
        any Space hit -> space-bms.ProjectBD                via ProjectSAPCode /
                                                            ProjectTempCode / ProjectName
        DMS file      -> space-attachment.Attachment        via AttachmentId
        buildtrack    -> assets.equipment                   via project_name STRING MATCH
      Cache: 60-second TTL, max 200 entries.

3. WHAT SHOULD I REUSE FROM THE POC
================================================================================

| POC Component | What it does | Should I reuse it? | Reason |
|---|---|---|---|
| Search logic / pipeline (global_search_core/pipeline.py) | analyze -> retrieve -> filter -> respond; connector-agnostic | YES — reuse the shape | Clean, small, framework-free orchestration. One line (pipeline.py:75-80) imports app.core.data_sources and must be cut. Needs a permission stage inserted. |
| Query understanding (query_intel.py) | Rule-based intent, content types, status hints, dynamic top_k | YES — highest value | Deterministic, fast, no LLM, no network. This is the single most portable asset. The keyword vocabulary must be re-derived for your real entity names. |
| Query planner (query_planner.py) | Picks SEMANTIC / FILTER / LIST_ALL / WORKFORCE mode | YES | Small, deterministic, prevents top-K truncation on "show me all X" queries. |
| Source selection (data_sources.select_sources_for_analysis) | content_type -> which sources to query | YES — the pattern | The approach is right. The specific maps are POC-specific and get rewritten. |
| Source router (routing/source_router.py) | Keyword scoring for DB vs TOOL | NO | Labelled "semantic" but is a keyword score. Not reliable enough to decide which real services to call. |
| Database search (connectors/*, core/data_sources engines) | 19 direct SQLAlchemy connections | NO | Every query runs with the same privileged DB account regardless of who is searching. This is the thing you are replacing with calls to your existing module APIs. |
| SQL agent (sql_agent/) | LLM writes T-SQL, then executes it | NO | LLM-authored SQL against production data, reachable from a 280ms typeahead, no user predicate, regex-only validation, not parameterised. |
| Azure AI Search — index schema (indexer.py ensure_index_exists) | Field definitions, HNSW 1536, semantic config | YES — reuse the schema | Well-shaped. The ACL field names already exist; you just have to actually populate them. |
| Azure AI Search — retrieval (retrieval.py hybrid_search) | BM25 + semantic + vector in parallel with timeouts | YES | The parallel strategy and the "skip embedding for short queries" gate are good engineering. |
| Azure AI Search — indexing pipelines (sql_indexer, space_indexer, assets_indexer, blob_indexer) | Push and pull indexers | NO | They read production DBs directly and write zero ACL data. The blob/RAG index has no definition in the repo at all. |
| Catalog (search/catalog/ + 5 YAML files) | Declarative entity definitions, field tiers, content hashing | YES — reuse the pattern | Good production pattern: what to index, what stays SQL-only, what the ACL fields are. Rewrite the entity files for your app. |
| Incremental sync (incremental_sync.py, sync_state.py) | Watermarks + content-hash gated embeddings | YES | Real cost control. Reuses the existing vector when search_text_hash is unchanged. |
| Embeddings (embeddings.py) | text-embedding-3-small, 1536 dims | YES — with fixes | Query-time gate is correct. Missing real batching and retry; "embed_batch" is just a loop. |
| Ranking (rerank_score) | Base score + hand-tuned boosts | YES — port the structure | This IS your search intelligence. But the weights are unvalidated and mix incomparable score scales, so they must be re-tuned. |
| Result merging (_merge_by_score) | Merge and sort across sources | PARTLY | Logic is fine but it sorts scores from different scales together. Needs score normalisation. |
| Deduplication | id, then content_type\|title\|source | PARTLY | Port the idea; key on sourceSystem+entityType+entityId instead of title. |
| Cross-database linking (cross_db_links.py) | ~16 hardcoded hops joined on ProjectId | NO (keep the idea) | The relationships are assumed, not verified, and it ADDS hits after filtering. Defer to v2 with real, confirmed relationships. |
| Search result model (global_search_core/models.py) | SearchRequest / SearchResponse / SearchResultItem | PARTLY | Shape is close to a normal SearchHit. Must drop `url`, add entityType/entityId/tenantId/partial/highlights. |
| Search API (routes/search.py) | 20 endpoints | PARTLY — 3 of 20 | Keep /results and /answer as concepts. The other 17 are admin operations that any logged-in user can currently call. |
| Search UI (SearchBar.tsx) | Debounce, dropdown, grouping, filter tabs, two-phase | NO the code, YES the behaviour | Your app already has a SearchBar, design system, api-client and routing. The POC component also has no ARIA combobox roles and no arrow-key navigation. Take it as a spec. |
| Frontend search SDK stub (lib/global-search/) | Types + createSearchClient + config | NO | Written but never imported. Your real search-sdk already does this. |
| Authentication (core/security.py, routes/auth.py, deps.py) | Own HS256 JWT, own login, open registration | NO — delete entirely | Would create a second login. Hardcoded fallback secret; caller can self-assign the Admin role. |
| Authorization (security_trim.py) | One project_id OData filter | NO — redesign | Called from one place, bypassed for Space sources, and disabled in the current config. Effectively no authorization runs today. |
| Configuration (core/config.py + .env) | pydantic-settings reading a local .env | NO | Live secrets on disk, no Key Vault, and a boolean that turns security off. |
| Logging (basicConfig INFO) | Plain Python logging | NO | No structure, no correlation ID, no App Insights, and it logs query prefixes and embedded-text prefixes. |
| Caching (6 in-process dicts) | Result, answer, embedding, index, cross-DB, user caches | NO | None are user-scoped and none work across replicas. Cross-user leakage today. |

6.2 "WHAT DOES THE REAL APP'S SEARCH BAR NEED TO SEND?"
--------------------------------------------------------------------------------

To make the existing search bar call this API AS IT IS TODAY, the minimum is:

  POST {globalSearchBaseUrl}/api/search/results
  Authorization: Bearer <token>
  Content-Type: application/json
  { "query": "<user input>", "top_k": 10, "filter_type": "all" }

That is genuinely all the POC needs. It is a very thin contract. But it only
works because the POC does almost no authorization — which is exactly why the
contract cannot stay this thin.

WHAT THE REAL APPLICATION MUST ACTUALLY SEND (and what the API must then do):

  1. The real application's JWT — not a POC token.
     The API must validate issuer, audience, signature (via JWKS), and expiry,
     and must extract user id, tenant id and roles from it.
     -> Today the POC would reject this token outright: it verifies against its
        own HS256 SECRET_KEY and then looks up "sub" in its own users table.
        A real app token will fail signature verification, and even if it passed
        the user lookup would find nothing. THIS IS A HARD BLOCKER, not a config
        change.

  2. Correlation id header — whatever name api-client already uses.
     -> The POC neither reads nor emits one.

  3. Tenant id header (if the platform is multi-tenant), even though the tenant
     should also be derived from the token, so that it can be asserted twice.
     -> The POC has no tenant concept anywhere.

  4. The query text.

  5. Paging parameters — the real bar will eventually need offset/cursor + limit,
     not just top_k.

  6. Optional entity-type filter, expressed in the REAL taxonomy, not the POC's
     ~30 invented content_type strings.

WHAT THE REAL APPLICATION MUST RECEIVE BACK (beyond what the POC returns):

  - entityType + entityId + sourceSystem, so the frontend can build the deep
    link itself using the existing search-sdk factory.
    -> Today the backend sends a ready-made `url`. If your app expects
       frontend-owned deep links, this field has to go away and be replaced.
  - partial: true/false + failedSources[], so the UI can say "some sources are
    unavailable" instead of silently showing fewer results.
    -> The POC has no such concept.
  - tenantId echoed back for assertion.
  - highlights, so the bar can bold the matched terms.
    -> The POC returns none, and its UI does no highlighting.
  - a normalised score, or no score at all.
    -> The POC's scores are not comparable across sources.
  - a totalCount computed AFTER permission filtering.
    -> The POC computes it after relevance filtering only.

7. FINAL ANSWER — THE FOUR LISTS

--------------------------------------------------------------------------------
A. TAKE FROM POC
--------------------------------------------------------------------------------
 1. Query understanding — query_intel.py analyze_query(), detect_content_types(),
    is_question(), extract_search_terms(), and the DOMAIN_SIGNALS keyword map.
    Rule-based, fast, no LLM. Re-derive the vocabulary for your entity names.
 2. Query planning — query_planner.py plan_query() and its retrieval modes,
    including the "exhaustive" mode so that "show me all X" is not truncated.
 3. Ranking structure — query_intel.py rerank_score(): base score plus typed
    boosts. Take the STRUCTURE and the list of signals. Re-tune the weights.
 4. Relevance thresholding — result_filter.py filter_results_for_query(), the
    min_score = max(8.0, top_score * 0.55) idea.
 5. Hybrid retrieval strategy — retrieval.py hybrid_search(): BM25 + semantic +
    vector in parallel, with the "only embed if it is a question or 5+ words"
    gate and the fast-path / deep-path split.
 6. Azure AI Search index schema — indexer.py ensure_index_exists(): the field
    list, HNSW 1536-dim vector profile, and semantic configuration.
 7. Catalog pattern — search/catalog/ loader + builder + YAML entity files:
    declarative field tiers, sql_only_fields, index_body_text, acl_fields, and
    the sha256 search_text hash.
 8. Incremental sync design — incremental_sync.py + sync_state.py: watermark per
    (source, entity) plus content-hash gating so unchanged rows are not
    re-embedded.
 9. Source-selection pattern — data_sources.select_sources_for_analysis():
    content type maps to sources, with explicit fan-out as the fallback.
10. Pipeline shape — global_search_core/pipeline.py: analyze -> retrieve ->
    filter -> respond, with the connector abstraction.
11. Two-phase search UX behaviour — fast results first (280 ms debounce, min 2
    chars), AI answer as a separate later request with an AbortController.
    Take the behaviour and the numbers, not the component.
12. Result grouping and filter-tab UX behaviour from the POC search bar, as a

--------------------------------------------------------------------------------
D. QUESTIONS I STILL NEED TO ANSWER
--------------------------------------------------------------------------------
 1. How is authorization actually enforced in the real application, and can
    Global Search reuse it, or must ACLs be duplicated into the search index?
    Everything else depends on this answer.
 2. Is the platform multi-tenant? The POC has no tenant concept at all, so
    nothing can be inferred from it.
 3. Which backend language and runtime will the Global Search service use? This
    decides whether the reusable parts are a port or a rewrite. (Dropping the
    SQL agent and the vision subsystem removes most of the Python-specific
    dependencies, so a rewrite is more feasible than it first looks.)
 4. Do the existing module search APIs actually cover the entities users want to
    search, and are they fast enough to fan out to on a typeahead?
 5. Which entity detail pages are URL-addressable? If most are not, clicking a
    result may have nowhere to go — that is a product problem to resolve before
    building.
 6. Is document/chunk search in scope for v1? If yes, the RAG index must be
    rebuilt from scratch, because the POC's was created in the Azure Portal and
    has no definition in this repository and no ACL fields.
 7. Are the cross-source relationships the POC assumes actually real in
    production? Specifically: does the same ProjectId mean the same project in
    every service? The POC never verified this beyond two manual probe scripts.
 8. What are the acceptable latency budgets? There are NO benchmarks anywhere in
    this repo, so the POC's real-world speed is unmeasured.
 9. How will search relevance be measured? There is no evaluation set in the POC
    — only a drawing object-count accuracy script. Without a set of real queries
    with expected results, the ranking weights cannot be safely re-tuned or
    regression-tested. This has the longest lead time of anything on this list;
    start collecting it early.
10. Should the AI answer feature ship in v1 at all, and if so who owns the LLM
    cost, the latency budget, and the data-residency approval?
