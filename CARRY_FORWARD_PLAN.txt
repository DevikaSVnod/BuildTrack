0. STRATEGY RESET — READ THIS FIRST
================================================================================

My earlier assessments ("NO-GO", "rebuild the backend") were written assuming the
target application was unknown and that its module APIs would be the integration
surface. The Jira CSV changes that picture in one decisive way:

    THE POC IS ALREADY READING THE REAL APPLICATION'S DATABASES.

The 17 DEV_V1_SPACE_* databases in backend/.env are SPACE's own databases. This
is not a POC talking to a toy dataset that must be re-pointed at production. It
is already pointed at production-shaped data, and per your Jira baseline story it
already has ~6.6k documents indexed in space-action-index and working ProjectId
hops across Project, HSE, Incident, LMS, CMS and Dashboard.

That means the correct move is NOT to rebuild. It is:

    PROMOTE the POC backend to "Global Search Service v1", then HARDEN it.

With 7 days you cannot rebuild, and you do not need to. What you must do is fix
the small number of things that are genuinely unsafe, and cleanly separate the
demo application scaffolding from the search service.

THE HONEST TRADE, STATED ONCE
  The one thing that is not negotiable even for a DEV demo is that two SPACE
  users with different project access must not see each other's data. Right now
  they do — verified: SEARCH_ENABLE_BUILDTRACK=false in backend/.env, and
  connectors/buildtrack.py:99-102 is the only caller of build_security_odata,
  so zero permission filtering executes today. Section 3 lists six fixes that
  close this. They are days of work, not weeks, and they are the difference
  between a demo you can show and a demo that leaks SPACE data in front of
  stakeholders.

  Everything else on the "ideal architecture" list — federating to module APIs,
  rebuilding the chunk index, replacing the SQL agent — is deferred to post-31-Aug
  and recorded in section 6 as UAT/PROD gates. That is the right call for the
  deadline, provided you write those gates down now rather than discovering them
  in UAT.

3. THE SIX NON-NEGOTIABLE FIXES BEFORE THE DEV DEMO
================================================================================

Ordered by risk. Fix 0 is independent of everything and should happen today.

  FIX 0 — ROTATE THE SECRETS.                              [today, 1 hour]
    backend/.env holds live values: DATABASE_URL and AZURE_SQL_CONNECTION_STRING
    with embedded passwords, SPACE_DATABASE_URL with on-prem SQL credentials,
    AZURE_OPENAI_KEY (84 chars), AZURE_OPENAI_EMBEDDING_KEY (84), AZURE_SEARCH_KEY
    (52, an ADMIN key), AZURE_STORAGE_CONNECTION_STRING (192). The file is
    gitignored (.gitignore:19) but the values are real and have been on a laptop
    and in a shared analysis. Rotate all of them.

  FIX 1 — VALIDATE THE SPACE TOKEN.                        [Jira story, 8h]
    Delete the POC's own JWT issuance. Validate SPACE's token: signature via
    JWKS, issuer, audience, expiry. Extract user id, roles, and tenant if SPACE
    has one. Fail closed - no token, no results, 401.

  FIX 2 — RESOLVE SCOPE ONCE PER REQUEST, FAIL CLOSED.
    Resolve the SPACE user's allowed project ids. Confirmed available in the
    schema: um.User_Assignment.ProjectId with IsActive, joined to um.Users.
    If scope cannot be resolved -> return empty, never return everything.
    Today security_trim.allowed_project_ids() returns [] on failure, which is
    correct behaviour; but build_security_odata() returns None (= unrestricted)
    for admin/PM roles, and that role mapping must be re-based on SPACE roles.

  FIX 3 — APPLY THE SCOPE ON EVERY PATH. This is the actual fix.
    Four paths currently bypass it:
      a) connectors/buildtrack.py:70   security_filter=None for Space sources
      b) sql_agent/                    no user predicate in generated SQL
      c) cross_db_links.py hops        privileged SQL, results appended after
                                       any filtering would have run
      d) blob_retrieval.py             no ACL field exists on the chunk index
                                       (defer the whole path instead)
    Every one must receive and enforce the resolved project id set.

  FIX 4 — PUT THE SCOPE HASH IN EVERY CACHE KEY.
    retrieval.py:47-57 and multi_database.py:99-105 both build keys with no user
    dimension, TTL 120s. answer.py's answer cache is 300s. Until this is fixed,
    User A's results are served to User B. This is a small change with a large
    consequence.

  FIX 5 — SPLIT THE ADMIN SURFACE.
    17 of the 20 endpoints in routes/search.py require only a valid token. A
    SPACE user with any role can today POST /api/search/index and trigger a full
    reindex, or POST /api/search/cache/clear. Move them behind an admin role.

  Suggested verification before the demo, in one sitting:
    Log in as two SPACE users on different projects. Run the same five demo
    queries as each. Diff the result sets. If they are identical, Fix 3 is not
    done. Then deliberately break the filter and confirm the test catches it.

5. WHAT THE ARCHITECTURE ACTUALLY IS AFTER 31 AUG
================================================================================

  SPACE application shell
      |
  SearchBar widget (packaged, props-driven, onOpenResult owned by SPACE)
      |
  SPACE JWT
      |
  Global Search Service  (the promoted POC backend, standalone)
      |
      +-- SPACE JWT validation
      +-- Entitlement resolution -> allowed project ids + scope hash
      +-- Query understanding (query_intel, rules only)
      +-- Source selection (data_sources)
      +-- Fan-out, scope-filtered on every path:
      |     - space-action-index (Azure AI Search, ACL fields populated)
      |     - schema-SQL against Space DBs (scope predicate forced)
      |     - cross-DB hops (scope predicate added)
      +-- Merge, rank (rerank_score), dedupe, relevance filter
      +-- Response { hits, total, partial, failedSources }
      |
  SPACE UI renders; SPACE owns navigation

  This is an index-plus-direct-read architecture, not the federated-API
  architecture I recommended earlier. That is a deliberate, deadline-driven
  choice and it is defensible ONLY because the scope filter is enforced on every
  path. Direct DB reads are not the problem; unfiltered direct DB reads are.
  Write that sentence into your go/no-go note so the trade is explicit.

6. GATES — DEV-ACCEPTABLE vs BLOCKS UAT vs BLOCKS PROD
================================================================================

  ACCEPTABLE FOR THE 31 AUG DEV DEMO
    In-process caching (single replica), provided the scope hash is in the key
    No Redis
    No Application Insights; basic structured logging
    No CI/CD; manual deploy with a runbook
    Schema-SQL LLM path, provided scope injection is mandatory and fails closed
    No relevance evaluation set
    Index ACL fields populated for space-action-index only

  BLOCKS UAT
    Any path that can return a record outside the user's scope
    Cross-user cache leakage
