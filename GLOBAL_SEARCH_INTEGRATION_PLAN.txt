WHAT CHANGED FROM THE EARLIER INVESTIGATION
Three earlier conclusions were refined or corrected by this pass:

  1. "The backend generates deep links." Only PARTLY true, and the true picture
     is worse. For the sources that are actually enabled today, hits carry
     url = "" (cross_db_links.py:407 and sql_agent/executor.py:128), and the
     Space index hits carry "/space/{table}/{id}" which has NO matching route in
     the POC frontend (there is no app/(dashboard)/space/ directory). So in the
     live configuration almost NO result has a working deep link.

  2. "Entity IDs are stable." Not on the dominant path. Schema-SQL hits get
     id = f"schema-sql-{source_id}-{i}" (executor.py:124) where i is the ROW
     POSITION in the result set. That id changes between queries for the same
     record. Deduplication, deep linking, and caching are all unreliable on that
     path. Real ids do survive, but only inside metadata via
     _promote_join_keys() (executor.py:37-85), which lifts project_id, user_id,
     document_id and attachment_id only.

  3. "The POC has no tenancy." Confirmed and now quantified: searching all 17
     schema snapshots found NO TenantId / OrgId / OrganizationId column in ANY
     database. Scoping is ProjectId, plus a CompanyId in the admin and UM
     databases only.

Additionally verified this pass: there is NO column named AssignedTo or
AssignmentOption in any of the 17 schema snapshots. This directly affects Part 9.

SHOULD THE FINAL APPLICATION'S GLOBAL SEARCH QUERY DATABASES DIRECTLY?

  NO. Five independent reasons, each grounded in the code:

  R1. It structurally cannot enforce authorization. Every source is opened with
      one privileged account (core/data_sources.py _create_engine_for_source).
      The identity of the person searching never reaches the SQL. The only ACL
      mechanism in the repo is bypassed on this path by
      connectors/buildtrack.py:70 passing security_filter=None.

  R2. It duplicates business rules that already live in the module services.
      Every hop in _SPACE_PROJECT_HOPS re-implements filters like
      "AND ISNULL(IsActive,1)=1", "AND IsDeleted=0", "AND ProjectId <> 0". Those
      predicates are a guess at each module's real visibility rules. When a
      module changes its rules, search silently diverges.

  R3. The cross-database relationships are assumed, not verified. The entire
      linking model rests on "the same numeric ProjectId means the same project
      in every database". The code itself already documents one exception —
      BMS uses ProjectBDID and matches by SAP code or name instead
      (cross_db_links.py:635-657). The only validation is two manual scripts
      (probe_cross_db_hops.py, smoke_pending_hops.py, the latter hardcoding
      ProjectId=15). There is no automated test.

  R4. It creates an operational coupling that will break. 17 connection strings
      derived by string manipulation, 17 connection pools inside the API
      process, and every cross-DB hop creating and disposing its own engine
      per query.

  R5. The LLM-SQL path is not safe to run against production. The validator is
      regex-based, the column allowlist is explicitly documented as "soft", the
      SQL is not parameterised, and no user predicate is injected.

PART 4 — INTEGRATION BOUNDARY
================================================================================

THE PROPOSED SHAPE

  Existing SearchBar → Global Search API → orchestration →
  existing module APIs / Azure AI Search → normalized results → existing UI

IS IT CORRECT? Yes in structure, but it is missing three stages that the POC's
failures prove are mandatory. The corrected boundary:

  Existing SearchBar
       ↓  (existing api-client: JWT, correlation id, tenant id, timeout, logout)
  Global Search API
       ↓
  [NEW] JWT validation — validate the EXISTING app token. Issue nothing.
       ↓
  [NEW] Entitlement resolution — user → {tenant, roles, principals, scope ids},
        short-TTL cached, hashed into an "entitlement fingerprint"
       ↓
  Query understanding (ported from query_intel.py, deterministic, no LLM)
       ↓
  Query routing (deterministic entity-type → capability map)
       ↓
  ┌──────────────────────────────┬────────────────────────────────┐
  │ Federated fan-out to module  │ Azure AI Search for document / │
  │ APIs, called WITH the user's │ long-text content, with a      │
  │ token so each service        │ MANDATORY server-injected ACL  │
  │ enforces its own rules       │ filter                         │
  │ - hard per-source deadline   │ - tenant_id + acl_principals   │
  │ - circuit breaker per source │ - never client-overridable     │
  └──────────────────────────────┴────────────────────────────────┘
       ↓
  [NEW] Permission assertion — defence in depth. Drop any hit that does not
        carry a tenant/scope attributable to this caller. Runs BEFORE ranking
        and BEFORE counting.
       ↓
  Normalization → entityType + entityId + sourceSystem. NO url.
       ↓
  Ranking (ported rerank_score structure, weights re-tuned, scores normalised
           across sources — the POC does not normalise and it shows)
       ↓
  Deduplication on sourceSystem + entityType + entityId
       ↓
  Response { hits[], total, partial, failedSources[], tookMs }
       ↓
  Existing UI → frontend-owned deep link via the search-sdk factory

WHY THE THREE ADDED STAGES ARE NOT OPTIONAL
  - Without entitlement resolution there is no cache key that is safe to share,
    and the POC's cache is provably unsafe today.
  - Without a permission assertion stage, a single mis-integrated source leaks
    everything it returns. The POC's hydrate.py already demonstrates the failure
    mode: it computes an authorization decision and then discards it.
  - Without score normalisation the merged ranking is arbitrary. The POC mixes
    raw Azure @search.score with hand-rolled boosts up to +40, schema-SQL scores
    starting at 1.0, and cross-DB scores fixed at 0.48, then sorts them together
    (multi_database.py:47).

ONE BOUNDARY DECISION THE POC ARGUES FOR: keep Global Search as a SEPARATE
service, not a module inside an existing API. The POC demonstrates that this
workload needs its own fan-out concurrency, its own timeout budget, its own
index lifecycle and its own ingestion worker. Embedding that into an existing
module API couples an unbounded fan-out to that module's request pool.

WHAT THE POC EXPOSES TODAY (verified, global_search_core/models.py)

  POST /api/search/results
  Request  { query, filter_type?, top_k (1..50, default 5), source_ids? }
  Response { ai_answer, results[], suggested_questions[], search_time_ms,
             total_results, is_question, sources_searched[] }

  Errors   400 empty query; 401 invalid token. No envelope, no codes.
  Paging   none. Partial failure   not represented. Timeout   none per source.

PROPOSED CONTRACT FOR THE TARGET APPLICATION

  POST /api/global-search
  Headers
    Authorization: Bearer <existing application JWT>   (required)
    X-Correlation-Id: <from the existing api-client>   (required)
    X-Tenant-Id: <from the existing api-client>        (required if multi-tenant;
                                                        asserted against the token)
  Request
    {
      "query":       "payment terms",        // required, trimmed, 1..256 chars
      "page":        { "limit": 20, "cursor": null },
      "filters": {
        "entityTypes": ["contract","document"],   // canonical taxonomy
        "projectIds":  [15],                      // narrowing only, NEVER widening
        "updatedAfter": "2026-01-01T00:00:00Z"
      },
      "options": { "timeoutMs": 2500, "includeFacets": false }
    }
    NOTE: no user id, no role, no source credentials, no "sourceIds". Identity
    and entitlements come only from the validated token. A client-supplied
    projectIds list may only INTERSECT with what the user can already see.

  Response 200
    {
      "query": "payment terms",
      "tookMs": 412,
      "partial": true,
      "failedSources": [{ "source": "lms", "reason": "timeout" }],
      "total": 37,                    // AFTER permission filtering; estimated
      "totalIsEstimate": true,
      "page": { "limit": 20, "cursor": "eyJvIjoyMH0=" },
      "hits": [
        {
          "sourceSystem": "cms",
          "entityType":   "contract",
          "entityId":     "4821",
          "title":        "Main Works Contract — Package 3",
          "snippet":      "…payment terms shall be net 30 days from…",
          "matchedContext": [
            { "field": "OtherImportantTermsOfContract",
              "text": "…<em>payment terms</em> shall be net 30…" }
          ],
          "score": 0.87,              // normalised 0..1 across all sources
          "updatedAt": "2026-07-14T09:12:00Z",
          "metadata": { "projectId": "15", "contractNo": "C-003" }
        }
      ],
      "facets": null
    }
    There is deliberately NO "url" field. The frontend builds the link from
    sourceSystem + entityType + entityId using the existing search-sdk factory.

  ERROR HANDLING
    400  invalid request      { code:"INVALID_QUERY", message, correlationId }
    401  token invalid/expired — the existing api-client already handles logout
    403  caller lacks the global-search entitlement
    429  rate limited, with Retry-After
    500  unexpected — must NEVER be returned merely because a source failed
    All errors share one envelope: { code, message, correlationId, details? }

  EMPTY RESULTS
    200 with hits: [], total: 0, partial: false. Never 404. If every source
    returned zero because of permissions, that is still 200/empty — the response
    must not reveal that hidden matches exist.

  PAGINATION
    Cursor-based, opaque, server-signed, encoding the per-source offsets. Offset
    paging cannot work correctly across a federated fan-out where sources return
    different counts. Recommended limit 20, hard maximum 50.

  TIMEOUT BEHAVIOUR
    Global budget from options.timeoutMs, hard-capped server-side (suggest
    1000 ms typeahead / 3000 ms full search). Every source gets a deadline
    strictly under the global budget. A source that misses its deadline is
    abandoned, not awaited. Contrast with the POC, where fut.result() is called
    with no timeout at all (multi_database.py:125).

  PARTIAL SOURCE FAILURE
    Always 200 when at least one source succeeded, with partial:true and
    failedSources populated so the UI can say "some sources are unavailable".
    Only when EVERY source fails should the call return 503. The POC currently
    logs the failure and returns a response indistinguishable from a full
    success (multi_database.py:119-128, 150-155).

PART 6 — SECURITY / PERMISSIONS  (critical)
================================================================================

HOW THE POC HANDLES AUTHORIZATION TODAY — verified line by line

  The complete list of permission checks in the repository is two items long.

  1. api/deps.py get_current_user() — "are you logged in and active?" Nothing
     more. With a 90-second cache keyed on the raw token, during which neither
     the signature nor is_active is re-checked.

  2. search/security_trim.py build_security_odata() — produces one OData string:
       (project_id eq '1' or project_id eq '2')
     Facts about it:
       - Called from exactly one place: connectors/buildtrack.py:99-102.
       - Returns None (unrestricted) for role "admin" or "project_manager"
         (security_trim.py:20).
       - BUG: UserRole.project_manager.value is "Project Manager", so .lower()
         produces "project manager" which never matches "project_manager".
         Project Managers are treated as RESTRICTED here, while hydrate.py:45-84
         treats them as UNRESTRICTED. The two paths disagree.
       - Only filters project_id. The index fields organization_id, tenant_id
         and access_groups exist and are filterable but are NEVER POPULATED by
         any indexing code.

  Everything else is unprotected:
       - connectors/buildtrack.py:70 passes security_filter=None for every Space
         source.
       - sql_agent/executor.py injects no user predicate into generated SQL.
       - cross_db_links.py hops run privileged SQL and APPEND hits after any
         filtering would have occurred.
       - hydrate.py _authorize_row() returns True when db is None, when
         project_id is None, and when user is None; and callers never drop a hit
         that fails it.
       - multi_database.py:99-105 caches merged results for 120 s under a key
         with no user in it.
       - answer.py _answer_cache (300 s) and embeddings._embed_cache are
         likewise global.
       - routes/files.py serves any document or drawing by id to any logged-in
         user.
       - config.py:118 SEARCH_SECURITY_TRIMMING is a boolean that switches
         authorization off.

  And in the CURRENT backend/.env, SEARCH_ENABLE_BUILDTRACK=false and
  SEARCH_ENABLE_ASSETS=false. Since buildtrack.py:99-102 is the only caller of
  build_security_odata, and BuildTrack is disabled, ZERO permission filtering
  executes on any search request today.

  Conclusion: two users with different permissions currently receive identical
  results. Authentication is present; authorization is effectively absent.

HOW GLOBAL SEARCH SHOULD PREVENT UNAUTHORIZED ACCESS

  Principle: the search service must never be the authority on what a user may
  see. It must either delegate that decision to the owning service, or enforce a
  filter derived from an authority it does not control.

  Layer 1 — Identity. Validate the existing application JWT: signature via JWKS,
  issuer, audience, expiry, and kid rotation. Derive user, tenant, roles and
  principals from claims only. Never accept identity from the request body.

  Layer 2 — Delegation for structured entities. Call each module's own search
  API with the caller's token (or an on-behalf-of token). The module applies its
  own authorization. This is the strongest option because it cannot drift from
  the module's rules.

  Layer 3 — Index-side trimming for content search. Where a module has no search
  API and content must be indexed, every indexed document carries:
      tenant_id        filterable, never null
      acl_principals   Collection(Edm.String), filterable
      scope_id / project_id, entity_type, entity_id, source_system, updated_at
  and every query has appended, server-side and non-overridable:
      tenant_id eq '<from token>'
        and acl_principals/any(p: search.in(p, '<principals from token>'))
  Chunks must inherit their parent document's ACL. The POC's blob/RAG index has
  no ACL field at all, so this pipeline has to be built, not adapted.

  Layer 4 — Assertion before ranking and counting. Drop any hit lacking an
  attributable tenant/scope. Compute total AFTER this stage. The POC computes
  total_results after the relevance filter only (pipeline.py:134).

  Layer 5 — Entitlement-aware caching. Cache key must include a hash of
  {tenant, principals, roles}. Any cache entry without it is a leak.

  Layer 6 — Admin separation. Reindex, sync and cache-clear operations move to
  an internal API requiring an admin role. In the POC all 17 such endpoints
  require only a valid user token.

CAN THE POC SAFELY USE EXISTING APPLICATION APIS THAT ALREADY ENFORCE AUTH?

  Architecturally yes — that is exactly the right design, and the POC's
  connector abstraction (global_search_core/connector.py SearchConnector ABC)
  is a suitable seam to plug API-backed connectors into.

  But it cannot be confirmed from this repository. The POC has never called a
  single module API; it only ever opened database connections. Nothing here
  demonstrates that the target APIs exist, expose free-text search, accept a
  delegated token, or return the fields needed.

  BACKEND TEAM CONFIRMATION REQUIRED:
    - Do the module search APIs enforce the caller's permissions server-side?
    - Is there an on-behalf-of / token-exchange flow for service-to-service
      calls that preserves the end user's identity?
    - Is there a bulk authorization API ("of these ids, which may this user
      see?") to support index-side trimming verification?
    - What is the authoritative source for a user's principals and visible
      scopes, and is there an API to resolve them?
    - Is the platform multi-tenant, and which claim carries the tenant?
      (The POC gives no help here: no TenantId column exists in ANY of the 17
      schema snapshots.)

WHAT DATA IS INDEXED
  buildtrack-index        One document per logical entity (project, task,
                          document, team member, handover, drawing, safety,
                          attendance, timeline, report/KPI). Selected fields
                          plus a metadata JSON string — not raw table dumps.
  buildtrack-assets-index Pre-flattened rows from buildtrack_assets.search_documents.
  space-action-index      action.* tables. Three tables get rich purpose-built
                          documents (Events, Event_Agenda, Event_Information);
                          all others get a generic builder that concatenates up
                          to 40 text columns, capped at 25,000 rows per table.
  space-schema-index      TABLE AND COLUMN DESCRIPTIONS. No business data.
  rag/blob index          Document chunks. Created by the Azure Portal wizard.
                          No definition, no field list, no skillset in this repo.

FIELDS (indexer.py ensure_index_exists — one schema shared by four indexes)
  key           id
  searchable    title, content, search_text
  filterable    content_type, progress_pct, record_status, entity_id,
                entity_type, source_database, updated_at, project_id,
                organization_id, tenant_id, access_groups, location, status
  facetable     entity_type, source_database, location, status
  sortable      progress_pct, updated_at
  retrievable   url, metadata, entity_id, entity_type, source_database,
                search_text_hash, updated_at, project_id
  vector        content_vector — Collection(Edm.Single), 1536 dims, HNSW
                profile "buildtrack-hnsw"
  semantic      configuration "default"; title=title, content=[search_text, content]
  NOT PRESENT   no scoring profiles, no suggesters, no custom analyzers

VECTORIZED FIELDS
  Only content_vector. Source text is search_text, or title+content when
  search_text is absent (indexer.py _add_vector).

EMBEDDING MODEL
  text-embedding-3-small, 1536 dimensions. Two generation paths:
    push  — the application calls embed_text() before upload
    pull  — an AzureOpenAIEmbeddingSkill in the skillset embeds /document/content
  Note the mismatch: the push path embeds search_text, the pull path embeds
  content. The same logical record can be vectorised from different text
  depending on which path indexed it.

HOW RECORDS GET IN
  Pull  Azure SQL indexer "buildtrack-sql-indexer" reading
        dbo.vw_global_search_documents on a PT15M schedule.
  Push  index_documents() SDK upload, batches of 50, used for assets, Space,
        schema, and the primary DB when it is not Azure SQL
        (sql_indexer.uses_push_indexing()).
  Blob  Portal-provisioned indexers found by name substring "blob" or "rag".

HOW UPDATES ARE HANDLED / IS INDEXING INCREMENTAL
  Push path: YES, genuinely incremental. Watermarks per (source, entity) in the
  search_sync_state table, plus sha256 content hashing so an unchanged
  search_text reuses the existing vector instead of re-embedding
  (indexer.py:26-35). This is the best-engineered part of the indexing design.
  Pull path: NO. The data source is documented as a FULL CRAWL EACH RUN
  (setup_sql_indexer.py:190-196) because change tracking on a view was not
  wired up. Every 15 minutes the entire view is re-read and re-embedded by the
  skillset, with no hash gating.

DELETED / CHANGED RECORDS
  No soft-delete detection policy is configured on the Azure indexer. Deletions
  are handled application-side:
    index_purge.py purge_stale_search_index() — reads valid ids from the SQL
    view, scans the index at top=1000, deletes the difference in batches of 500.
    index_purge.py delete_sql_backed_row() — immediate delete by id.
  This means a row deleted in the database stays searchable until someone runs
  the purge. There is no schedule for it.

HOW MUCH DATA IS EXPECTED
  UNKNOWN — NEEDS VERIFICATION. No row counts exist in the repo. The only sizing
  signal is SPACE_INDEX_MAX_ROWS_PER_TABLE = 25000 and the schema snapshots,
  which show the table counts per database: lms 76, um 34, cms 34, chkwp 29,
  incident 17, action 16, dms 15, project 4. Table counts are not row counts.

COST / PERFORMANCE CONCERNS
  1. The 15-minute full crawl re-embeds everything, every run, forever. This is
     the single largest avoidable cost in the design.
  2. Two embedding paths mean two cost centres and inconsistent vectors.
  3. The generic Space builder indexes up to 40 columns per row across every
     discovered table — indexing volume is driven by schema shape, not by
     search value.
  4. Query-time embedding fires whenever the query is a question or has 5+
     words, adding an Azure OpenAI round trip to those searches.
  5. embed_batch() is a sequential loop, so bulk ingestion is serialised.
  6. No retry or backoff on any OpenAI call; a 429 simply drops the vector.
  7. One admin key serves both query and admin traffic.

CAN THIS INDEXING/SEARCH ARCHITECTURE BE REUSED?

  PARTIALLY — reuse the design, rebuild the pipelines.

  REUSE AS-IS (design and code both portable)
    - The index field schema in ensure_index_exists(), including the vector and
      semantic configuration. The ACL field NAMES are already correct.
    - The hybrid query strategy in hybrid_search(): parallel BM25 + semantic +
      vector, with the "skip the embedding for short non-question queries" gate.
    - The catalog pattern in search/catalog/: declarative per-entity field
      tiers, sql_only_fields, index_body_text, acl_fields, deterministic
      search_text and its sha256 hash.
    - The incremental sync design: watermark table + content-hash gated
      embedding reuse.

  MUST CHANGE
    - Populate tenant_id, acl_principals and scope ids at index time. Today
      organization_id, tenant_id and access_groups are declared and never
      written by any code path.
    - Promote project_id/scope to a real filterable field on the PULL path. The
      SQL indexer maps only id, title, content, content_type, url, metadata,
      progress_pct and record_status; project_id stays inside the metadata JSON
      string, which cannot be filtered.
    - Replace the full crawl with high-water-mark change detection, or move
      everything to the push path which already has watermarks.
    - Rebuild the blob/RAG index from scratch in IaC, with an explicit chunking
      configuration and ACL inheritance onto every chunk. There is nothing to
      port — it does not exist in this repository.
    - Add a scheduled purge, or a soft-delete policy, so deletions propagate.
    - Split the admin key from the query key, or use managed identity.
    - Stop indexing the space-schema-index entirely; it exists only to feed the
      LLM SQL agent, which is being dropped.
    - Add batching and retry to embedding generation.
    - Remove URL fields from indexed documents.

  No. Three separate reasons:

  visibility semantics. This is not a search-team task. Do not attempt to
  reconstruct it from the schema.

PART 11 — RECOMMENDED FINAL ARCHITECTURE
================================================================================

EVALUATION OF THE FOUR OPTIONS

  A. Frontend → module APIs → merge in the browser
     Authorization    GOOD — each API enforces its own rules
     Relevance        POOR — no cross-source ranking possible in the client
     Latency          POOR — N round trips from the browser, worst-case serial
     Scalability      POOR — fan-out cost paid per client, no shared cache
     Maintainability  POOR — search logic duplicated in a large React monorepo
     Freshness        EXCELLENT — always live
     Indexing cost    ZERO
     Complexity       Deceptively low at first, high once ranking is needed
     VERDICT: rejected. It also drifts toward client-side filtering, which is
     explicitly out of bounds.

  B. Frontend → Global Search API → module APIs → merge
     Authorization    EXCELLENT — delegated, cannot drift from module rules
     Relevance        MODERATE — limited to what each API's own search returns
     Latency          MODERATE — one client round trip, bounded server fan-out
     Scalability      MODERATE — bounded by the slowest module API
     Maintainability  GOOD — one place owns orchestration
     Freshness        EXCELLENT — always live
     Indexing cost    ZERO
     Complexity       MODERATE
     VERDICT: strong, but it cannot do document-content or clause-level search,
     because no module API will full-text a 2000-character contract clause or a
     PDF body.

  C. Frontend → Global Search API → Azure AI Search only
     Authorization    RISKY — everything depends on index-side trimming being
                      perfect, and the POC proves how easily that is skipped
     Relevance        EXCELLENT — one ranked corpus, hybrid + semantic
     Latency          EXCELLENT — one index query
     Scalability      EXCELLENT
     Maintainability  MODERATE — a large ingestion estate to own
     Freshness        POOR — bounded by indexing lag
     Indexing cost    HIGH
     Complexity       HIGH
     VERDICT: rejected as the sole architecture. Making it the only path means
     every module's authorization must be re-implemented as index metadata, and
     the POC demonstrates that the moment ACL population is optional, it does
     not happen.

  D. Hybrid — structured entity search via APIs, document/content via AI Search
     Authorization    GOOD — delegated where possible; explicit, designed
                      trimming only where unavoidable, on a small surface
     Relevance        GOOD — live precision for entities, semantic recall for
                      content
     Latency          GOOD — parallel, with per-source deadlines
     Scalability      GOOD — the expensive index covers only content
     Maintainability  GOOD — clear ownership split
     Freshness        GOOD — entities live; content bounded by indexing lag,
                      which is acceptable for documents
     Indexing cost    MODERATE — only content is indexed, not every table
     Complexity       MODERATE-HIGH — two retrieval paths to normalise and rank
                      together
     VERDICT: chosen.

CHOSEN: ARCHITECTURE D — HYBRID

  Rationale grounded in this repository:
    - Part 8 shows the entity modules already have stable bigint ids, direct or
      one-hop project scoping, and short text. Those are cheap and safe to
      federate live. Indexing them buys little and costs ACL correctness.
    - Part 8 also shows CMS has eleven nvarchar(2000) clause fields and DMS has
      nvarchar(MAX) keyword and content fields. That is real long-form content
      where BM25 plus vector plus semantic ranking genuinely outperforms a
      LIKE-based module API. That is worth indexing.
    - Part 6 shows the POC's failure mode is optional authorization. Hybrid
      minimises the surface where authorization must be re-implemented, and
      concentrates it in one place that can be reviewed and tested properly.
    - Part 7 shows the reusable index machinery (schema, hybrid query,
      incremental sync, catalog) is already aimed at exactly this: content
      discovery, with the database as the source of truth. Two feature flags in
      config.py, SEARCH_HYDRATE_FROM_SQL and SEARCH_CATALOG_ENABLED, show the
      POC was already drifting toward this split.

  Boundary rule to enforce, stated once:
    Structured entities → live module APIs, called with the user's identity.
    Long-form content (documents, drawings, contract clauses) → Azure AI Search
    with mandatory server-injected tenant + ACL filters.
    Nothing queries a database directly from a user request, ever.

================================================================================
EXECUTIVE DECISION
================================================================================

1. WHAT ARCHITECTURE SHOULD WE USE?
   Architecture D — Hybrid. Structured entity search federates live to the
   existing module APIs, called with the user's own identity so each service
   enforces its own authorization. Long-form content — documents, drawings, and
   contract clauses — goes to Azure AI Search with mandatory, server-injected
   tenant and ACL filters. A dedicated Global Search service owns orchestration,
   permission assertion, normalization and ranking. No user request ever touches
   a database directly.

2. SHOULD GLOBAL SEARCH DIRECTLY QUERY DATABASES?
   No. Not in a user request, under any circumstance. The POC's 19 privileged
   connections cannot enforce authorization, duplicate business rules that
   already live in the module services, and rest on an unverified assumption
   that the same ProjectId means the same project in every database. If a module
   turns out to have no search API, index it from an offline ingestion worker
   with its own service account that writes ACL fields — never read it from the
   request path.

3. SHOULD WE CREATE A NEW GLOBAL SEARCH API?
   Yes — a separate service, not a module inside an existing API. The workload
   needs its own fan-out concurrency, its own timeout budget, its own index
   lifecycle and its own ingestion worker. Embedding an unbounded fan-out inside
   an existing module's request pool would couple that module's availability to
   every other module's. The public surface should be small: one search endpoint,
   optionally one answer endpoint, and a separate admin API. Not the POC's 20
   endpoints, 17 of which any logged-in user can currently call.

4. SHOULD WE REUSE THE POC'S AZURE AI SEARCH?
   Reuse the design; rebuild the pipelines. Take the index field schema, the
   1536-dimension HNSW vector configuration, the semantic configuration, the
   hybrid BM25 + vector + semantic query strategy, the declarative catalog
   pattern, and the watermark-plus-content-hash incremental sync — that last one
   is the best-engineered thing in the repository. Do not reuse any of the five
   indexing pipelines: they read production databases directly and write no ACL
   data. The ACL field names already exist in the schema and are never populated
   by any code path; populating them for real is the central change. The
   blob/RAG chunk index cannot be reused at all — it was created in the Azure
   Portal and has no definition in this repository.

5. WHAT IS THE FIRST THING WE SHOULD IMPLEMENT?
   Not code. First, get the JWT specification and the authorization model
   confirmed (P0-1 and P0-2) — the POC would reject a real application token
   outright, and it currently applies zero permission filtering, so both are
   hard blockers rather than configuration changes. In parallel, and starting
   today because it has the longest lead time and no dependencies, build the
   relevance evaluation set: 100-200 real queries with labelled expected
   results. The POC's hand-tuned ranking boosts are its genuine intelligence and
   there is nothing anywhere in this repository to validate them against.
   The first thing to BUILD, once P0-1 through P0-3 are answered, is the Phase 1
   vertical slice: existing SearchBar through to the Action Meeting module API
   and back, with authorization and partial failure proven on that one source
   before a second source is added.
