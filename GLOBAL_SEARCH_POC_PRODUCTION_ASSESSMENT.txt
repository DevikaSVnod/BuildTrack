VERDICT (read this first)
================================================================================

NO-GO -- BLOCKED BY INFORMATION, and additionally BLOCKED BY AUTHORIZATION DESIGN.

Two independent blockers:

BLOCKER 1 (technical, in the POC):
  The POC has effectively NO working authorization on the search path in its
  current configuration. It cannot be promoted, wrapped, or "hardened later".
  The permission model must be designed before any code is written.
  Evidence:
    - security_trim.py is the ONLY ACL mechanism. It builds a single OData
      filter: project_id eq 'N' or project_id eq 'M'.
    - It is called from exactly ONE place: connectors/buildtrack.py:99-102.
    - That path is explicitly bypassed for all Space sources:
      connectors/buildtrack.py:70  ->  security_filter=None
    - In the current backend/.env, SEARCH_ENABLE_BUILDTRACK=false and
      SEARCH_ENABLE_ASSETS=false; only the 17 Space DBs are enabled.
      => Today, ZERO permission filtering runs on any search request.
    - The LLM-generated SQL path (sql_agent/) executes against Space DBs with
      NO user predicate injected at all (sql_agent/executor.py).
    - hydrate._authorize_row() (search/hydrate.py:45-84) fails open in three
      branches ("return True" when db is None, when project_id is None, when
      user is None) and callers NEVER DROP a hit that fails it.
    - The multi-DB result cache key contains no user/entitlement dimension
      (connectors/multi_database.py:99-105) -> User A's results can be served
      to User B for 120s.

BLOCKER 2 (information, from the real application):
  Nine facts are required before design can be finalised. They are listed in
  section "O. QUESTIONS TO ASK THE BACKEND/PLATFORM TEAM" and summarised in
  "MUST HAVE BEFORE DEVELOPMENT". Chief among them: the production backend
  architecture and runtime are unknown, so we cannot yet say whether a Python
  service is deployable at all.

WHAT IS SALVAGEABLE: the search *intelligence* (query understanding, ranking
heuristics, hybrid retrieval strategy, index schema shape, catalog/ incremental
sync design, two-phase UX pattern). That is real, non-trivial, and worth
porting. Roughly 25-30% of the POC by value; the plumbing around it is not
production material.

B. POC SEARCH FLOW (actual traced implementation, query = "payment terms")
================================================================================

 1. SearchBar.tsx onChange -> 280ms debounce (RESULTS_DEBOUNCE_MS), min 2 chars.
    No AbortController on the fast-search request (only on the AI request).
 2. lib/api.ts searchApi.searchFast -> POST {API}/api/search/results
    Headers: Authorization: Bearer <cookie buildtrack_token>. Timeout 60s.
    NO correlation ID header. NO tenant header.
 3. routes/search.py fast_search() -> Depends(get_current_user).
    deps.py: 90s in-memory cache keyed by the RAW JWT string; on cache hit the
    signature is NOT re-verified and is_active is NOT re-checked.
    Context built = {"db": session, "user": User}.
 4. pipeline.search_results() -> analyze_query() (query_intel.py).
    Pure rules: DOMAIN_SIGNALS keyword map, STATUS_WORDS, QUESTION_STARTERS,
    regex for drawing numbers / progress / manager. No LLM.
 5. select_sources_for_analysis() narrows by content_type. "payment terms"
    matches no narrow rule -> FALLS BACK TO ALL ENABLED SOURCES (17 Space DBs).
 6. MultiDatabaseConnector.retrieve(): checks the shared _search_cache with key
    md5(query|filter|top_k|analysis_suffix|"multi:<source ids>").
    *** NO USER IDENTITY IN THIS KEY. *** TTL 120s.
 7. Cache miss -> ThreadPoolExecutor(4).submit per source, as_completed().
    Per-source try/except returns ([], error_string). NO per-source timeout
    (fut.result() has no timeout argument). Errors are logged only.
 8. Per Space source -> retrieve_space_hybrid():
      - source_router.route_query() keyword score -> DB / TOOL / BOTH
      - if SCHEMA_SQL_ENABLED and looks_structured_db_query():
          schema_catalog/search.py search_relevant_tables()
             -> may embed the query (Azure OpenAI embedding call)
          sql_agent/generator.py generate_select_sql()
             -> *** AZURE OPENAI CHAT CALL, gpt-4o-mini, temp 0, 600 max_tokens ***
          sql_agent/validator.py validate_select_sql() (regex read-only guard,
             table allowlist, forced TOP N; column allowlist is explicitly soft;
             SQL is NOT parameterised)
          sql_agent/executor.py execute_readonly_sql() (15s timeout, 50 rows)
      - optional Azure index hybrid_search() with security_filter=None
 9. Merge: _merge_by_score() dedupes on id, then on
    "content_type|title.lower()|database_id". Sort by score desc. Cap top_k*2.
10. cross_db_links.attach_related_hits(): fans out ~16 hardcoded SQL hops across
    sibling Space DBs joined in-memory on ProjectId. Cap top_k*4+24.
11. result_filter.filter_results_for_query(): RELEVANCE filter (min_score =
    max(8.0, top_score*0.55)). This is NOT a permission filter.
12. pipeline._to_items(); total_results = len(filtered).
    *** totalCount is therefore computed after relevance filtering but never
        after permission filtering. ***
13. Frontend renders grouped by content_type, 3 per group preview.
14. Click -> router.push(result.url) where url came from the BACKEND.
15. Separately, at 1200ms debounce (or immediately if the query is a question),
    SearchBar fires POST /api/search/answer -> generate_answer() -> chat LLM.
    IMPORTANT: pipeline.search_with_answer() calls generate_answer(raw) BEFORE
    filter_for_display(). The LLM therefore sees the UNFILTERED hit set.


================================================================================
C. CORE SEARCH INTELLIGENCE WORTH REUSING  (port this)
================================================================================

C1. Query understanding - query_intel.py + query_planner.py
    Deterministic, no LLM, no network. DOMAIN_SIGNALS keyword->content_type map,
    question detection, status/progress/manager/drawing-number extraction,
    dynamic top_k. This is domain knowledge earned over the POC and is the
    single most reusable asset. Port as a pure library with unit tests.
    Caveat: the vocabulary is BuildTrack/Space specific and must be re-derived
    against the real application's entity names.

C2. Ranking heuristics - query_intel.rerank_score()
    Formula is: final = azure_base_score + sum(boosts). Notable boosts:
      content_type in analysis.content_types      +12   (miss: -10)
      workforce query and hit is team             +20   (other types: -25)
      project qualifier match ratio >= 0.6        +10   (>=0.3: +3, miss: -12)
      status hint present in title/snippet        +5    (in metadata.status: +6)
      exact upload-date match                     +30
      document-content query + document type      +28 + title-match score
      blob RAG chunk + question                   +20   (long snippet: +10)
      drawing-content query + drawing type        +40 + drawing-match score
      token overlap with question                 +min(overlap*0.8, 4.0)
    Thresholds: min_score = max(8.0, top_score * 0.55)  (0.72 for "which drawing")
    Fetch: SEMANTIC_FETCH_MIN=20, SEMANTIC_FETCH_MAX=40, EXHAUSTIVE_CAP=100.
    These weights are hand-tuned and undocumented. PRESERVE THE STRUCTURE, but
    they MUST be re-tuned against a real evaluation set (which does not exist -
    see K).

C3. Hybrid retrieval strategy - retrieval.py hybrid_search()
    Runs BM25 + semantic + vector in parallel and merges, with a "fast path"
    (BM25 only, 8s cap) vs "deep path" (semantic + keyword, 10s cap each) chosen
    by query shape. Query embedding is skipped for short non-question queries
    (gate: analysis.is_question OR len(query.split()) >= 5). Good instinct -
    keep this gate.

C4. Index document design - search/catalog/ (loader, builder, models + 5 YAML
    entity files: project, task, document, drawing, material)
    Declarative per-entity field tiers, sql_only_fields, index_body_text flag,
    acl_fields declaration, deterministic search_text + sha256 content hash.
    This is a genuinely good production pattern. Reuse the pattern; rewrite the
    entity definitions for the real application.

C5. Incremental sync design - incremental_sync.py + sync_state.py
    Watermark table search_sync_state (source, entity, watermark ISO timestamp)
    + content-hash gating that reuses the existing vector when search_text_hash
    is unchanged (indexer.py:26-35). Genuinely reduces embedding cost. Reuse.

C6. Azure AI Search index schema shape - indexer.py ensure_index_exists()
    Field set (id key, title, content, content_type, url, metadata JSON,
    search_text, search_text_hash, entity_id, entity_type, source_database,
    updated_at, project_id, organization_id, tenant_id, access_groups, location,
    status, progress_pct, record_status, content_vector[1536] HNSW profile
    "buildtrack-hnsw", semantic config "default"). The ACL FIELD NAMES ARE
    ALREADY THERE - they are simply never populated. Reuse the schema, populate
    the ACL fields for real.

C7. Two-phase search UX - fast results first, AI answer as a separate
    lower-priority request with its own debounce and AbortController.
    Correct pattern. Port the pattern, not the component.

C8. Partial-failure instinct - multi_database.py per-source try/except so one
    dead source does not fail the request. Right idea, incomplete execution
    (no timeout, no partial flag) - see section on error handling.

D. POC COMPONENTS THAT MUST NOT BE PORTED
================================================================================

D1. The entire authentication stack.
    core/security.py, api/routes/auth.py, api/deps.py.
    HS256 with a hardcoded fallback secret ("buildtrack-super-secret-jwt-key",
    config.py:18). Token carries only {sub, exp}. No iss, no aud, no kid, no
    verification of issuer/audience, no refresh. OPEN /api/auth/register that
    lets the caller choose their own role including Admin. This would be a
    second login mechanism. DELETE IT ENTIRELY.

D2. Direct multi-database access.
    core/data_sources.py, core/space_databases.py, connectors/multi_database.py.
    19 configured sources (buildtrack, assets, and 17 Space DBs) each opened
    with a full SQLAlchemy engine using credentials from .env, with sibling DB
    URLs DERIVED BY STRING-SWAPPING THE DATABASE NAME on a base connection
    string. Every query runs with the same privileged DB account regardless of
    who is searching. This bypasses every authorization rule the real backend
    services enforce. MUST BE REPLACED by federated calls to existing module
    APIs.

D3. The LLM SQL agent.
    sql_agent/ (generator, validator, executor).
    An LLM writes T-SQL against production schemas and it is executed. The
    validator is regex-based; the column allowlist is explicitly "soft"; the SQL
    is not parameterised; there is no user/tenant predicate. Also, this LLM call
    sits on the /search/results path, i.e. on the typeahead critical path.
    DO NOT PORT. If natural-language-to-SQL is wanted later it is a separate
    product with its own security review.

D4. The POC frontend search UI.
    components/layout/SearchBar.tsx (1027 lines) plus SearchResults.tsx and
    AIAnswer.tsx (both already dead code, imported nowhere).
    The real application already has a SearchBar, design system, api-client,
    auth SDK, routing, loaders and error UI. Bring the BEHAVIOUR (debounce
    values, two-phase pattern, grouping, filter tabs, empty state) as a written
    spec; bring no TSX. The POC UI additionally has no ARIA combobox/listbox
    roles and no arrow-key navigation, so it is not a quality baseline.

D5. Backend-generated SPA URLs.
    URLs are baked into index documents and patched during enrichment:
      indexer.py:306   "url": f"/projects/{project.id}"
      indexer.py:410   "url": f"/documents?docId={doc.id}"
      document_enrich.py:164 / :272, blob_retrieval.py:373-378,
      cross_db_links.py:1177 / :1241, space_indexer.py:461 "/space/{table}/{id}"
    The backend owns SPA routing today. If the real application expects
    frontend-owned deep links, this must be inverted (see section on the
    result model).

D6. cross_db_links.py as written.
    ~16 hardcoded SQL hops with hardcoded schema names, table names and join
    columns, plus 5 hardcoded demo project-name aliases (PROJECT_ALIASES,
    cross_db_links.py:51-57), plus name-string matching between BuildTrack and
    the assets DB. Assumes numeric ProjectId means the same project in every
    Space DB - unverified except by two manual probe scripts. The IDEA (related
    records across sources) is worth keeping; the implementation is not.

D7. All in-process caches.
    retrieval._search_cache, answer._answer_cache, embeddings._embed_cache,
    index_reader._cache/_doc_cache, cross_db_links._lookup_cache,
    deps._user_by_token. None are user-scoped, none survive restart, none work
    behind more than one replica.

D8. Drawing vision / object inventory subsystem.
    object_inventory.py (2832 lines), drawing_vision.py, drawing_sheet_intel.py,
    drawing_text_extract.py, inventory_validate.py, aspose-cad, PyMuPDF,
    pypdfium2, Pillow. This is a CAD/vision feature, not global search, and it
    can issue dozens of vision calls per request when it runs live at query
    time (drawing_vision.py:805 and :948 call extract_object_inventory()).
    Out of scope for Global Search v1.

D9. Admin/index-management endpoints as designed.
    POST /api/search/index, /space-index, /assets-index, /schema-index,
    /blob-index, /sync/incremental, /cache/clear, GET /metrics, /plugins,
    /sources, /catalog. ALL of these require only a valid JWT - no role check.
    Any authenticated contractor can trigger a full reindex or clear the cache.
    These belong on an internal/ops surface with admin authorization, not on the
    user-facing search API.

EVERY PERMISSION CHECK IN THE POC (exhaustive list - there are only two):
  1. api/deps.py get_current_user  -> "are you logged in and active?"
  2. search/security_trim.py build_security_odata -> project_id OData filter,
     invoked from connectors/buildtrack.py:99-102 only.
     - Returns None (= unrestricted) for role "admin" or "project_manager".
     - BUG: UserRole.project_manager.value is "Project Manager", so
       .lower() yields "project manager", which does NOT match the
       {"admin","project_manager"} set at security_trim.py:20. Project Managers
       are silently treated as restricted here while hydrate.py treats them as
       unrestricted. The two ACL paths disagree.
     - Returns [] (= see nothing) when db is None.
     - Only ever filters on project_id. organization_id, tenant_id and
       access_groups exist as filterable index fields but are NEVER POPULATED
       at index time and NEVER USED in a filter.

ANSWER TO "CAN THIS POC SAFELY RUN FOR TWO USERS WITH DIFFERENT PERMISSIONS?"

  NO.

  With the current backend/.env (BuildTrack and Assets disabled, 17 Space DBs
  enabled): User A, User B and Admin receive IDENTICAL results for an identical
  query. The only difference between users is whether they can call the API at
  all. There is no per-user partitioning of any kind.

  Even if BuildTrack were re-enabled, it would still be unsafe:
    - Space sources hardcode security_filter=None (buildtrack.py:70).
    - The LLM-SQL path injects no user predicate.
    - cross_db_links hops run unfiltered privileged SQL and ADD hits to the
      result set after the (already absent) filter.
    - The multi-DB cache is not user-scoped -> cross-user result leakage
      within a 120s window.
    - answer._answer_cache (300s) and embeddings._embed_cache are likewise
      global; the generated AI answer for a query is reused across users.
    - generate_answer() runs on the raw, unfiltered hit list, so the LLM can
      summarise content the user is not entitled to see even if the result list
      were later trimmed.

  Do NOT interpret "search works when logged in" as "search is authorization
  safe". These are separate properties and only the first holds.

AZURE AI SEARCH SECURITY TRIMMING -- EXPLICIT STATEMENT

  CURRENT POC INDEXING IS NOT SUFFICIENT FOR PRODUCTION AUTHORIZATION.

  Per index:
    buildtrack-index        project_id populated ONLY on the push/catalog path.
                            The pull SQL indexer maps only id/title/content/
                            content_type/url/metadata plus progress_pct and
                            record_status - project_id is NOT promoted to a
                            top-level filterable field, it stays inside the
                            metadata JSON string, which cannot be filtered on.
    buildtrack-assets-index no ACL fields populated (material.yaml acl_fields: [])
    space-action-index      no ACL fields populated
    space-schema-index      no ACL fields populated (schema descriptions)
    rag/blob index          Portal-provisioned, not defined in this repo.
                            Fields consumed are chunk_id, parent_id, chunk,
                            title, text_vector. NO ACL FIELD AT ALL. Document
                            chunks are therefore completely untrimmed.

  MINIMUM METADATA THAT MUST BE ADDED TO EVERY INDEXED RECORD BEFORE PRODUCTION:
    tenant_id            filterable, always populated, never null
    acl_principals       Collection(Edm.String), filterable - the flattened set
                         of group/role/user principal IDs allowed to see the row
    project_id / scope_id  filterable, populated for every scoped entity
    entity_type, entity_id, source_system   filterable (already present)
    visibility / classification  filterable (public / internal / restricted)
    updated_at, deleted_flag     for freshness and soft-delete trimming
  And the production query must ALWAYS append, server-side and non-overridable:
    tenant_id eq '<from JWT>' and acl_principals/any(p: search.in(p, '<user principals>'))
  The blob/RAG index needs the same fields propagated onto every chunk, which
  means the chunk pipeline must inherit ACLs from the parent document. That
  pipeline does not exist in this repo (it was built in the Azure Portal wizard).

H. API CONTRACT RECOMMENDATION
================================================================================

POC contract as built (global_search_core/models.py):
  Request   { query, filter_type?, top_k (1..50, default 5), source_ids? }
  Response  { ai_answer, results[], suggested_questions[], search_time_ms,
              total_results, is_question, sources_searched[] }
  Result    { id, title, snippet, content_type, url, metadata?, score? }
  Errors    400 on empty query; 401 from the auth dependency; 503 from index
            endpoints. No error envelope, no error codes, no pagination
            (top_k only, no offset/cursor), no partial-failure signalling.

Gap analysis vs the production SearchHit/SearchResult and vs the stated
production constraints:

  ADD
    tenantId                     required, echoed from the validated JWT
    entityType + entityId        replaces the "id" string; enables frontend
                                 deep-link factories
    sourceSystem                 which module answered (POC has this only as
                                 metadata.database_id)
    partial: boolean             REQUIRED by the "200 + partial:true" constraint
    failedSources: string[]      which sources degraded, for UI messaging
    highlights: {field, spans[]} POC returns no highlight data at all; the UI

    updatedAt / timestamp        POC has updated_at in the index but never

    correlationId echo           to match the existing api-client convention

    url                          backend must stop owning SPA routes (D5)
    ai_answer from /results      keep the two endpoints strictly separate
    suggested_questions          LLM-derived, belongs on the answer endpoint
    source_ids in the request    letting a client choose sources is an
                                 authorization smell; the server should decide

  TRANSFORM

                      taxonomy, not the POC's ~30 ad-hoc TYPE_CONFIG strings
    score          -> normalised 0..1 across sources (POC mixes raw Azure

I. INFRASTRUCTURE REQUIREMENTS
================================================================================

I1. RUNTIME -- THE BIGGEST UNRESOLVED RISK.
    The POC is Python 3.11 / FastAPI and needs the Microsoft ODBC Driver 18 for
    SQL Server plus native wheels (pyodbc, PyMuPDF, pypdfium2, Pillow,
    aspose-cad) baked into the image. If the platform team does not already run
    Python services, introducing one means new base images, new dependency
    scanning, new runtime patching, new on-call knowledge, and a new language in
    the estate. DO NOT ASSUME THIS IS FREE.
    Three options must be priced before committing:
      (a) Deploy a Python container - fastest if containers are already the
          deployment unit and the platform accepts a Python image.
      (b) Reimplement the Global Search service in the platform's existing
          backend language, porting the intelligence from C1-C8. The reusable
          logic is mostly deterministic string/keyword/scoring code and ports
          cleanly. This is the safer long-term option if Python is unwelcome.
      (c) Hybrid - port the orchestrator to the house language, keep nothing
          from Python.
    NOTE: dropping the LLM-SQL agent and the drawing-vision subsystem removes
    most of the heavy Python-specific dependencies, which makes (b) much more
    viable than it first appears.

I2. Azure AI Search service (or an approved equivalent) with: index definitions
    under source control, provisioned by IaC not by the Portal wizard (the POC's
    blob/RAG index was created by the Portal and has NO definition in the repo -
    it is unreproducible today).
I3. Azure OpenAI (or approved LLM) for the answer endpoint ONLY, plus an
    embeddings deployment for ingestion. Server-side only; the frontend must
    never hold these credentials (the POC frontend correctly holds none - keep
    it that way).
I4. Azure Key Vault (or platform secret store) + managed identity. No .env.
I5. Redis or an equivalent shared cache, for entitlement-scoped result caching
    across replicas. The POC's in-process dicts cannot work behind a load
    balancer.
I6. Blob storage for document content, with the chunking/ingestion pipeline
    defined in code and version-controlled.
I7. Application Insights / OpenTelemetry with correlation-ID propagation from
    the existing api-client. The POC has none.
I8. CI/CD pipeline. The POC has none.
I9. Network path from the Global Search service to every module API it federates
    to, plus to Azure AI Search. Private endpoints where policy requires.
I10. An ingestion/indexing worker separate from the request-serving process. The
    POC runs indexing as asyncio tasks inside the API process.

SLOWEST COMPONENTS IN THE SEARCH PATH, IN ORDER
  1. LLM SQL generation on /search/results (sql_agent/generator.py). A chat
     completion with no timeout, reachable from a 280 ms typeahead debounce.
     This alone disqualifies the current design for typeahead.
  2. Cross-DB link expansion (cross_db_links.py). Up to ~16 sequential SQL hops
     across sibling databases, each creating and disposing its own engine (no
     pool reuse), executed inside the request.
  3. Query-time embedding (up to 4 s wait) whenever the query is a question or
     has 5+ words - which is common.
  4. Fan-out to 17 sources through a 4-worker pool: the pool is smaller than the
     source count, so sources queue behind each other, and there is no per-source
     deadline, so the slowest source sets the total latency.
  5. Live drawing vision at answer time (drawing_vision.py:805, :948) can trigger
     dozens of vision calls in one request.
  6. Azure AI Search semantic ranking (10 s cap) on the deep path.

STRUCTURAL RISKS BEYOND LATENCY
  - Cross-source score comparability. Azure @search.score, hand-rolled boosts up
    to +40, and a SQL "hits + title_hits*1.5" score are merged and sorted
    together in _merge_by_score. Ranking quality across sources is therefore
    arbitrary. Score normalisation must be designed; it does not exist.
  - Thread pools are module-level globals shared across all requests. Under
    concurrency they become the bottleneck and there is no queue-depth limit or
    backpressure.
  - Everything is synchronous FastAPI (def, not async def) doing blocking I/O,
    so requests occupy the threadpool for their full duration.
  - The 60 s frontend timeout means a hung LLM call presents to the user as a
    one-minute spinner.


================================================================================
M. MISSING INFORMATION (what blocks safe implementation)
================================================================================

M1. The production authorization model. Roles, groups, scopes, project/tenant
    membership, document ACLs, and how they are represented. Without this the
    ACL fields cannot be defined and the index cannot be built.
M2. The production tenancy model. Is it single-tenant per deployment, or
    multi-tenant with a tenant claim? The POC's User model has NO tenant field,
    so nothing can be inferred from it.
M3. The production JWT specification: issuer, audience, signing algorithm, key
    distribution (JWKS endpoint? static key? kid rotation?), exact claim names
    for user id / tenant / roles, lifetime, and the refresh mechanism.
M4. The production backend architecture and runtime. Explicitly stated as
    unknown. This gates the entire deployment decision (I1).
M5. The contracts of the existing module-specific search APIs: paths, request
    shapes, response shapes, pagination, filtering, sorting, latency
    characteristics, rate limits, and whether they accept on-behalf-of calls.
    Federation is impossible to design without these.
M6. The canonical entity taxonomy and stable entity identifiers in production.
    The POC invented ~30 content_type strings and prefixes ids with
    "{source_id}::". Neither will match production.
M7. Which entity detail pages are URL-addressable, and the deep-link factory
    contract in search-sdk. Most detail pages are stated to be NOT fully
    URL-addressable - so for many entity types there may be no navigable target
    at all, which is a product problem, not just an engineering one.
M8. Whether document/drawing content search is actually in scope for v1. If yes,
    the blob/RAG index must be rebuilt from scratch with ACL propagation to
    chunks, because the POC's chunk index was created via the Azure Portal and
    has no definition in this repo and no ACL fields.
M9. Non-functional targets: typeahead p95 latency budget, full-search p95,
    acceptable staleness for indexed content, expected QPS, and the LLM cost
    ceiling for the answer feature.
M10. Data residency / compliance constraints on sending content to Azure OpenAI
    and on storing content in an external search index.
